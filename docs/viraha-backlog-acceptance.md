# Viraha 后续事项与验收标准

> 更新日期：2026-07-10
>
> 本文是 Viraha 的实施 Backlog。每个事项必须同时满足“代码完成、自动验证、人工验收”三类条件，才能标记为完成。

## 当前基线

已具备：记忆与关系、跨渠道身份合并、事件持久化与 Trace Cockpit、工具策略接口、插件清单加载、同用户串行队列、流式回复、Smoke Eval、主动消息重试，以及 SQLite 持久化任务 Scheduler。

当前自动验证基线：`pnpm build`、`pnpm test`、`pnpm lint`、`pnpm --filter @viraha/arete eval:smoke` 均应通过。

## Gate 0：统一产品定位

**问题**：现有文档存在冲突。

- `docs/v2/vision-and-roadmap.md`：Arete 是官方健身陪伴示例。
- `docs/superpowers/plans/2026-07-10-viraha-companion-quality.md`：Arete 被重新定义为情感陪伴示例。

**待办**：在仓库中确定并公开唯一结论：

1. Arete 保持健身陪伴，另建 `Echo` 作为情感陪伴参考实现；或
2. Arete 改为情感陪伴，并迁移/移除健身身份与技能；或
3. Arete 成为可切换的多领域参考实现，并定义每种身份的安全边界。

**验收标准**：

- [ ] `README`、`docs/v2/vision-and-roadmap.md`、`apps/arete/src/identity.ts` 对 Arete 的定位完全一致。
- [ ] 只保留与该定位匹配的默认技能、知识包、欢迎语和 Eval 数据集。
- [ ] 新用户能在首屏或 README 中明确知道 Arete 能做什么、不能做什么。
- [ ] 由维护者人工确认一次产品定位，不以代码测试代替决策。

## P0：可真实使用的陪伴闭环

### 1. 真实渠道上线与回执

**目标**：让用户能在飞书或 QQ 中稳定收发消息，而不是只在测试 Adapter 中运行。

**交付物**：一个已配置的真实渠道 Adapter、入站签名校验、出站发送结果记录、失败日志。

**验收标准**：

- [ ] 新用户首次给 Bot 发消息后，获得稳定内部 `userId` 和 channel binding。
- [ ] 同一用户连续发送两条消息时，第二条不会在第一条回复前越过执行。
- [ ] Bot 能发送回复，并在事件库中写入 `AgentResponseSent` 或等价出站事件。
- [ ] 临时渠道 API 失败时，错误会进入 Trace；进程不会崩溃。
- [ ] 在真实飞书或 QQ 环境手工完成“发消息 -> 收回复 -> Web 查看同一条 trace”的演示。

### 2. 持久化主动服务

**目标**：主动关怀任务在重启、短暂网络失败后仍可恢复，不产生重复骚扰。

**当前状态**：Scheduler、任务类型隔离、Presence 重试已实现；仍需生产级运行策略。

**交付物**：任务重试策略、任务状态查询、运行指标、可配置调度频率。

**验收标准**：

- [ ] 任务在写入 SQLite 后关闭进程，再启动后仍可被领取。
- [ ] worker 在 lease 超时后能回收 `running` 任务，且同一时刻不会被两个 worker 同时执行。
- [ ] 发送失败时遵守指数退避和最大重试次数；超过上限进入可查询的失败状态。
- [ ] 同一用户在一个冷却窗口内不会收到两条相同类型的主动消息。
- [ ] Trace Cockpit 能显示 queued/running/failed/completed 数量，以及最近失败原因。
- [ ] 自动测试覆盖重启恢复、重复领取、退避重试、冷却去重四种场景。

### 3. 隐私、身份与数据边界

**目标**：陪伴数据默认可解释、可删除、不会意外暴露给其他用户。

**交付物**：Web 身份会话策略、数据导出/删除 API、最小化日志策略、隐私说明。

**验收标准**：

- [ ] 不同 Web 用户的 profile、memory、relationship 和 trace 无法通过 API 互相查询。
- [ ] 用户可导出自己的记忆、关系摘要和事件记录，格式为 JSON。
- [ ] 用户可删除自己的数据；删除后重新查询不返回旧记录。
- [ ] 日志和 Trace 不打印 Provider API Key、Cookie 或渠道签名。
- [ ] README 明确说明本地 SQLite、外部模型 Provider 和数据发送边界。

### 4. 安全边界（仅当 Gate 0 选择情感陪伴或通用陪伴）

**目标**：危机、自伤、诊断、强依赖等场景具备固定且可观察的安全处理。

**交付物**：身份硬边界、透明规则扫描、安全事件、危机场景 Eval。

**验收标准**：

- [ ] 自伤、伤人、处方/诊断请求触发硬边界，不返回可执行的危险步骤。
- [ ] 回复包含关怀和寻求当地专业/紧急帮助的引导，不使用冷冰冰的拒绝模板。
- [ ] 每次触发在 EventStore 写入高优先级安全事件，并可在 Trace Cockpit 过滤。
- [ ] 中英文危机场景 Eval 全部通过；任何一项失败都阻止发布。
- [ ] 规则词表和响应策略可审阅，不依赖不可解释的黑盒分类器。

## P1：陪伴质量与长期关系

### 5. 记忆质量生命周期

**目标**：记忆不仅能保存，还能被正确检索、衰减、纠错和遗忘。

**交付物**：语义检索、记忆置信度、淡化/恢复规则、用户纠错入口。

**验收标准**：

- [ ] 用户在第一轮提供的长期事实，在独立后续会话中可被正确召回。
- [ ] 相似但不同的人物、时间或偏好不会被错误合并。
- [ ] 用户说“我不再喜欢/请忘记 X”后，后续提示词和检索结果不再使用 X。
- [ ] 低置信度或过期记忆不会无条件注入系统提示词。
- [ ] `eval:memory` 至少包含 20 个跨轮案例，整体通过率不低于 90%。

### 6. 关系与语气稳定性

**目标**：陪伴会随关系成熟而更自然，但不越界、不虚构亲密度。

**交付物**：关系等级与提示词映射、不同 persona 的可选策略、语气 Eval。

**验收标准**：

- [ ] 同一用户在不同关系等级的系统提示词能看到可解释的差异。
- [ ] 用户未建立关系时，回复不使用过度亲昵称呼或声称不存在的共同经历。
- [ ] 用户切换 persona 后，历史记忆仍保留，表达风格发生预期变化。
- [ ] `eval:tone` 覆盖温暖、克制、鼓励、边界四类场景，确定性检查全部通过。
- [ ] 使用真实 Provider 的抽样评估中，安全与尊重自主性均不低于既定阈值。

### 7. Arete 领域质量

**目标**：若 Gate 0 保留 Arete 的健身定位，确保其建议可信、保守且个性化。

**交付物**：运动限制规则、训练/营养评测集、知识包来源说明。

**验收标准**：

- [ ] 用户的伤病、可用时间、器械条件会进入建议上下文。
- [ ] 高风险动作或超出能力的计划会被替换为保守方案，并说明原因。
- [ ] 训练与营养建议不得伪装成医疗诊断或处方。
- [ ] 领域 Eval 覆盖伤病、初学者、减脂、增肌、时间不足四类场景，全部通过。
- [ ] 知识包条目可追溯到可信来源或明确标记为经验性建议。

## P1：工程可观测性与可靠性

### 8. Trace Cockpit 完整度

**目标**：开发者能用一个界面理解一轮对话、工具调用和主动任务发生了什么。

**交付物**：按 correlationId 的时间线、任务视图、安全/错误高亮、基础指标。

**验收标准**：

- [ ] 一次聊天可从用户输入追溯到 LLM、工具、回复、反思和关系更新事件。
- [ ] 一次主动任务可看到入队、领取、执行、发送、重试或完成状态。
- [ ] 高优先级错误和安全事件在列表中有明显视觉标记。
- [ ] 默认页面在 1000 条事件内仍可筛选并在 2 秒内返回本地结果。
- [ ] 所有用户可见 payload 使用安全 DOM 写入，不把用户文本拼入 `innerHTML`。

### 9. Provider 健康与降级

**目标**：外部模型短暂不可用时，系统知道发生了什么，并可按策略恢复。

**交付物**：Provider 状态 API、超时/失败指标、fallback 策略、用户友好错误。

**验收标准**：

- [ ] `/api/provider-health` 展示模型、Provider、失败数和 circuit 状态。
- [ ] 主 Provider 连续失败达到阈值后，不再持续发送无效请求。
- [ ] 配置备用 Provider 时，主 Provider 失败可自动切换并写入 trace。
- [ ] 没有可用 Provider 时，用户收到明确可行动的提示，服务进程仍保持运行。
- [ ] Provider Registry 的成功、失败、熔断、恢复均有自动测试。

## P2：开发者生态

### 10. Companion Pack 规范

**目标**：第三方可用稳定格式构建自己的领域陪伴，而不是修改 Arete 源码。

**交付物**：pack manifest v1、模板项目、加载校验、示例 companion pack。

**验收标准**：

- [ ] 一个独立目录仅通过 `pack.json` 和文档化资源即可被加载。
- [ ] manifest 的名称、版本、技能、知识包、persona 校验失败时给出定位到字段的错误。
- [ ] 示例包可在干净环境中加载并响应一个真实工具调用。
- [ ] 包工具不能绕过 `ToolPolicy`。
- [ ] 发布一个“从零创建 companion pack”的 15 分钟教程并由新环境验证。

### 11. SDK 与示例应用

**目标**：开发者能在少量代码内创建、运行和测试一个新陪伴。

**交付物**：稳定 `@viraha/sdk` API、最小示例、API 文档、端到端样例测试。

**验收标准**：

- [ ] 从空目录安装依赖、复制示例、配置一个 Provider 后可启动。
- [ ] 示例包括 identity、memory、channel、tool policy 和 trace 的最小配置。
- [ ] SDK 公共 API 有类型声明和至少一个使用测试。
- [ ] README 的每条启动命令在干净环境中可执行。

## P2：发布与运维

### 12. 可部署性

**目标**：从本地 Alpha 进入可重复部署、可诊断、可回滚的服务。

**交付物**：Docker Compose、环境变量校验、健康检查、备份/恢复说明。

**验收标准**：

- [ ] 一条文档化命令可在新机器启动 Web、数据库和已配置渠道。
- [ ] 启动时缺少必要环境变量会给出明确错误，不会静默回退到无效状态。
- [ ] 健康检查覆盖数据库、Provider 配置和 Scheduler worker。
- [ ] 备份 SQLite 后可恢复记忆、关系、事件和待执行任务。
- [ ] 发布前必须通过 `docs/release-checklist.md` 中全部自动与人工项目。

## 执行规则

1. 每个事项先写失败测试，再写实现。
2. 每个事项完成后至少运行受影响 package 的测试；阶段完成后运行全量构建、测试、lint 和 Eval。
3. 有真实渠道、真实 Provider、隐私删除、危机处理的事项必须附人工验收记录；自动测试不能替代。
4. P0 未完成前不扩展 marketplace、多智能体编排或华丽 UI。
5. 每次发布更新 `docs/release-checklist.md`，并记录通过日期、环境和已知限制。
